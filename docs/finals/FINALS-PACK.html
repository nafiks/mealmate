3 · CHEAT — Artur (Project Lead)

Мои строки

"76 kilograms per person per year — UNEP 2021." · "Every tester found a recipe in under two minutes." · "Next: a fridge scanner with real computer vision — a prototype is already live."

Ответы комиссии

How do you know the problem is real? Three sources: UNEP Food Waste Index 2021 (76 kg/person/year, Kazakhstan); a 2021 study of 244 students across five Almaty universities linking food security to well-being; and our own tests — three external testers all completed the core task.
What did YOU personally do? I owned the problem: research, evidence, priorities, acceptance. After UX tests I pushed three concrete fixes — clearer ingredient selection, an explicit finish state, visible navigation. I kept scope honest: we cut features instead of claiming unfinished ones.
How are you different from Supercook / Yummly? Local cuisine first-class (beshbarmak, kuurdak, baursaki); the honest two-list result with exact missing items; full Kazakh and Russian interface. Global services barely cover any of this.
Business side? Today — a student project on free hosting. The pattern that can earn: delivery integration ("2 ingredients away from these dishes") and university partnerships for dorms. Honest: monetization is not built yet.
Emergency "Outside my layer — my teammate owns it, and we would verify with data first." · Demo breaks → backup tab localhost:3001, or the promo video.

4 · CHEAT — Arsen (Frontend)

Мои строки

"You tick your ingredients — it instantly splits 68 recipes into 'cook right now' and 'almost there'." · "Kazakh cuisine is first-class — and it works in three languages." · "The scanner camera is real; the AI recognition is simulated — our honest next step."

Ответы комиссии

What did YOU personally do? The entire client layer: a hand-written CSS design system (no UI kit), all pages — picker with live matching, catalog, recipes, diary, community — and full trilingual localization including cooking steps. Plus the fixes our tests exposed: a pantry sync race, a quick-add bug, category overflow.
Why React, not plain HTML or mobile? The picker is one reactive state machine — ticking a chip must update matches instantly. Web over mobile because zero installation is our core requirement; a Capacitor wrapper would give app stores later without a rewrite.
How does localization work? Two layers. Content: localized DB columns (title_ru, name_kk, steps too) — the API picks with ?lang, English fallback. Interface: one shared dictionary. Units and phrases — "a pinch", "ас қасық" — localized separately.
What is simulated or unfinished? Honestly: scanner recognition is client-side simulated (camera and UI are real); guest diary photos reset on hosting restarts (ephemeral disk); password-reset emails are shown on screen — no mail service yet.
How are images handled? In the browser before upload: canvas downscale to 1280 px, JPEG quality 0.82 — a 5 MB phone photo becomes ~200 KB. Server re-validates format and size.

5 · CHEAT — Adilet (Database)

Мои строки

"We built it with React, Node.js and SQLite — zero installation." · "Seven tables — and the ingredient matching itself runs in SQL."

Ответы комиссии

Why SQLite and not PostgreSQL? Honest engineering: our load is a university demo — SQLite gives real persistence with zero administration, and the driver is built into Node. All SQL sits behind one thin module (db.js), so moving to PostgreSQL means rewriting that one file. We already avoid SQLite-only features.
Show the ER model. What would you change live? Seven entities: users, ingredients, recipes, two M:N junctions, instruction blocks, photo diary — plus reset tokens. Live change example: add servings_scale to recipe_ingredients so users can cook for three instead of two — one column, no schema break. The editable source is docs/er-diagram.dbml — paste at dbdiagram.io.
Where is the matching logic — DB or code? In SQL. Two CTEs: req counts required ingredients per recipe (non-optional, non-staple); got counts the user's overlap. missing = total − have. Zero → "cook now", 1–2 → "almost there". Filters run in the same query.
Relevance guarantee — what if I tick only bacon? Two guards: have ≥ 1 — a recipe appears only if at least one required ingredient is selected; and with a tiny selection the "almost" threshold adapts — otherwise one bacon tick would hide carbonara because three items are missing.
Data integrity? FK with ON DELETE CASCADE; UNIQUE e-mail; UNIQUE (recipe_id, step_number); indexes on junctions and diary; parameterized queries only.

6 · CHEAT — Sanzhar (Backend & Security)

Мои строки

"…we protect users by hashing passwords with scrypt, signing session cookies, and rate-limiting brute-force attacks." · "Testing: three UX problems found, three fixed. Database audit: two ingredients with zero recipes — ten recipes added, coverage zero gaps."

Ответы комиссии

What did YOU personally do? Every API endpoint — ingredients, matching, auth, pantry, diary, community feed. The security stack: scrypt hashing, HMAC-signed cookies, headers, rate limits, input validation. And the content pipeline: 68 recipes with nutrition and three-language steps, seeded into the database.
How are passwords stored? scrypt — a memory-hard KDF built into Node — with a unique random salt per user, compared with a timing-safe check. A database leak gives salted hashes; brute-forcing each costs heavy memory and time.
Sessions without a login server? Signed cookie: user id + expiry, HMAC-SHA256 with a server secret. httpOnly (JS cannot read it) + SameSite=Lax. Guests use the same mechanics with a guest row; registering upgrades that row — their pantry carries over.
Demonstrate one security scenario. Brute force: rapid wrong passwords at /api/auth/login — first forty get 401, request forty-one gets HTTP 429 for the rest of the window. scrypt makes each offline guess cost ~100 ms of CPU. Safe scenario: our own deployment, test account — no third-party systems touched.
How did you use AI and verify it? Disclosed in every assignment. AI wrote code, seed content and the coverage workbook. Verified by running: recipes reviewed against real cooking logic, endpoints tested with live requests, the Assignment-4 numbers come from database queries I can re-run here. Honest gaps — simulated scanner AI — are disclosed inside the product.
What if the database leaks? Worst case: usernames, e-mails, salted scrypt hashes and public recipe data. No plaintext passwords, no payment data. Sessions survive — they are signed with a server-side secret, not DB content.
