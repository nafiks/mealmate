# Шпаргалка к защите MealMate (CS-2618)

## 1. Питч (30 секунд)

«MealMate — веб-приложение для студентов, которые живут отдельно и не знают, что
приготовить из того, что уже есть дома. Пользователь отмечает продукты — приложение
мгновенно делит рецепты на "можно готовить сейчас" и "почти готово" (показывая, чего
именно не хватает). Без установки и без обязательной регистрации. 68 рецептов пяти
кухонь, КБЖУ, три языка (EN/РУ/ҚАЗ), фото-дневник и лента сообщества».

## 2. Живая демо-сценарий (отрепетируй 2 раза!)

1. Открыть `/` → показать hero, нажать «Find recipes».
2. На `/kitchen` отметить **картофель, лук, яйца** → справа сразу: «Crispy Fried
   Potatoes» в «Можно готовить сейчас» (кольцо 2/2 — соль и масло уже учтены как
   базовые), ниже «Почти готово» с томатными чипсами «+ Bread», «+ Butter».
3. Открыть рецепт → детальные шаги, ингредиенты с состояниями ✓/+, КБЖУ-бары.
4. Переключить язык на ҚАЗ или РУ (всё, включая шаги).
5. «Сохранить рецепт» без входа → редирект на логин (объяснить: персональные данные
   — только для аккаунтов, гость ничего не теряет).
6. Войти → действие продолжается само.
7. `/community` → лента готовок других пользователей.

## 3. Архитектура (рисуй на доске так)

```
Браузер (React SPA, Vite-сборка)
   │  HTTP/JSON (fetch, same-origin; в dev — прокси Vite)
   ▼
Express (Node.js)  ── маршруты: /api/ingredients, /api/recipes,
   │                 /api/auth, /api/pantry, /api/diary(+feed)
   ▼
SQLite (node:sqlite) ── 7 таблиц = ER-модель из Assignment 3
```

- **Почему React**: без установки, работает на любом устройстве, переиспользование компонентов.
- **Почему Node**: один язык с фронтендом, логика матчинга в одном месте.
- **Почему SQLite**: персистентность без сервера БД; слой `db.js` тонкий — замена на
  PostgreSQL не требует правки роутов. (На вопрос «почему не PostgreSQL»: для учебного
  объёма SQLite надёжнее и проще в деплое; миграция описана в README.)
- **Хостинг**: Railway (один сервис: API + статика SPA + volume для БД); альтернатива
  Vercel (фронт) + Railway (API) — уже поддержано `VITE_API_URL` и `CORS_ORIGIN`.

## 4. База данных (знаешь ER — знаешь всё)

7 таблиц из ER-модели Assignment 3, связи 1:N и M:N через junction-таблицы:
- `users` (1) → (N) `user_ingredients` (N) ← (1) `ingredients`
- `recipes` (1) → (N) `recipe_ingredients` (N) ← (1) `ingredients`
- `recipes` (1) → (N) `instruction_blocks` (UNIQUE step_number в рецепте)
- `users` (1) → (N) `photo_diary` (N) ← (1) `recipes`
Бизнес-правила: уникальный e-mail; номер шага уникален в рецепте.
**Расширения поверх ER** (честно говорим «расширения, не ломающие модель»):
`is_staple` (соль/масло/сахар не считаются «не хватает»), КБЖУ, `tags`, `featured`,
локализованные колонки (`title_ru/kk`, `name_ru/kk`, `description_ru/kk` в шагах),
`app_meta` (секрет сессий), `reset_tokens` (сброс пароля).

## 5. Алгоритм матчинга (главный вопрос комиссии)

Два CTE в одном SQL-запросе:
- `req`: на рецепт — сколько **обязательных** ингредиентов (optional=0, is_staple=0);
- `got`: сколько из них есть у пользователя;
- `missing = total − have` → `0` = «можно готовить сейчас», `1–2` = «почти готово»;
- **гарантия релевантности**: `have ≥ 1` — рецепт попадает в выдачу, только если
  минимум один его обязательный ингредиент у пользователя есть (это лечит баг
  «выбрал креветки — показывает блюда без креветок»);
- при выборе 1–2 продуктов порог «почти готово» адаптивно расширяется, чтобы
  релевантные блюда не скрывались (например, один бекон → карбонара с not хватает 3);
- фильтры (время/кухня/тег/поиск) применяются в том же запросе.

## 6. Безопасность (cybersecurity из roadmap — сделано)

- Пароли: **scrypt** + индивидуальная соль, сравнение timing-safe.
- Сессии: **HMAC-SHA256** подписанные httpOnly-куки (90 дней), без внешних JWT-библиотек.
- Гостевые аккаунты: пишешь кладовую/дневник → автоматически создаётся guest-строка;
  при регистрации гость **апгрейдится** — данные переносятся.
- helmet (заголовки), rate-limit на auth и загрузки, лимит JSON-тела, валидация всех
  входов, только параметризованный SQL, фото сжимаются в браузере до JPEG ≤ ~3 МБ,
  запись дневника отклоняется для гостя (не только в UI).

## 9. Вероятные вопросы и ответы

- **«Почему не мобильное приложение?»** — Веб: без установки и сторов, любой девайс;
  обосновано в Assignment 1 (Solution 1).
- **«Откуда рецепты и КБЖУ?»** — Ручная kurация команды, КБЖУ — приближённые значения
  на порцию, честно помечены «≈». Риск маленькой БД озвучен в Assignment 1.
- **«Что если два человека отметят одно и то же?»** — Кладова персональна (user_id),
  у каждого своя; лента сообщества показывает только фото с именами.
- **«Как хранятся фото?»** — Браузер сжимает до JPEG (макс. 1280px), data-URL в БД;
  для прод-масштаба — вынести в объектное хранилище (честная roadmap).
- **«Почему гости могут пользоваться?»** — Снижение порога входа (нашли в тестах);
  персональное (дневник/сохранённые) — требует аккаунта, гостевые записи приватны.
- **«Что дальше?»** — Coverage-отчёт для админа (из Assignment 4), избранное на сервере,
  PostgreSQL при росте, PWA-офлайн.
